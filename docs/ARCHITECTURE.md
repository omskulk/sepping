## Mental model

Three actors, two screens each at most:

| Role   | Start state                         | Screens                              |
| ------ | ----------------------------------- | ------------------------------------ |
| Active | 10 ping credits, 0 completedPings   | Active home (map + my pings) + drop dialog |
| PNM    | 0 ping credits, 0 completedPings    | PNM home (assigned pings) + detail + proof submission |
| Both   | —                                   | Leaderboard (read-only)              |

Everything is driven by **three Firestore collections** (`users`, `pings`) and one
**Storage prefix** (`pings/{pingId}/proof`). There are no Cloud Functions in the MVP —
every write originates from the client inside a Firestore transaction. This is
documented as a weakness below; fixing it is a v2 concern.

## The auth gate is the brain

`lib/screens/shared/auth_gate.dart` is the only place that decides what you see.
It has two layers:

1. **`StreamBuilder<User?>`** on `FirebaseAuth.authStateChanges()` — are we logged in?
2. If yes, **`StreamBuilder<AppUser?>`** on `/users/{uid}` — what role?

When the user doc loads, it's injected with `Provider<AppUser>.value(...)` so *any*
downstream widget can `context.watch<AppUser>()` to get the current user's profile —
including live updates when credits change. This is why you'll see the credit chip in
the app bar tick down the instant a ping is dropped: the Firestore snapshot update
propagates through the provider and rebuilds the chip.

## The ping-drop transaction

`PingService.dropPing()` runs inside a `runTransaction`:

1. Read the active's `/users/{uid}` doc.
2. If `pingCredits < creditCost`, throw `InsufficientCreditsException`.
3. Create a new `/pings/{auto-id}` document.
4. Decrement the active's `pingCredits` by the cost.

If any step fails, Firestore aborts the whole thing, so credits stay in sync with
pings. This is client-side — a malicious user could open the console and write
anything that passes the rules. The rules (`firestore.rules`) enforce:

- Only Actives can create pings.
- A ping must be authored by the creator (no impersonation).
- Initial `status` must be `pending`.

But the rules **cannot** enforce "decrement by exactly the ping's cost." That's a
known integrity gap. See v2 notes below.

## Proof submission transaction

`PingService.submitProof()`:

1. Upload bytes to `pings/{id}/proof` in Cloud Storage.
2. Get the download URL.
3. Transaction:
   - Re-read the ping; if already completed, return silently (idempotent).
   - Read the PNM's user doc.
   - Update the ping with `status=completed`, `photoUrl`, `completedAt`.
   - Increment the PNM's `completedPings`.

Same caveat: the PNM could skip the upload and bump their own counter manually in
a malicious client. Acceptable for MVP; addressed in v2.

## UI patterns worth noting

- **Side-by-side layout**: `active_home.dart` uses `LayoutBuilder`; at ≥900 px wide
  the map and list sit side-by-side. Below that they stack vertically. This avoids
  writing a tablet/mobile split.
- **All lists are `StreamBuilder`**: every ping/user list auto-refreshes when
  Firestore changes. No pull-to-refresh needed.
- **Error surfacing**: each mutation sets a local `_error` string and renders it in
  danger red under the form. FirebaseAuth errors get translated via
  `AuthService.describeError`.
- **Credit chip in the app bar** is fed from the `Provider<AppUser>` injected by the
  auth gate, so it updates live without being on the same screen as the mutation.
- **Leaderboard sorts client-side** to avoid needing a Firestore composite index
  (fine at chapter scale; would not scale to 10k users).

## What's NOT in this MVP (intentional punts)

- **Cloud Functions for atomic credit/completion bookkeeping.** Client transactions
  are trust-based. Move to Callable Functions + App Check if abuse shows up. See
  `SETUP.md` for how to enable Functions when you're ready.
- **Admin approval workflow for proof photos.** Right now submitting a photo
  auto-completes the ping and auto-awards the leaderboard point.
- **Push notifications** ("you've been pinged"). FCM is possible on Flutter web but
  adds a notable integration step; skipped for MVP.
- **Ping expiration / cancellation** — pings live forever once created.
- **Real-time location tracking** — we only use map tap coords; no background GPS.
- **iOS / Android builds** — web only for this sprint. The code is compatible with
  mobile with one exception: `image_picker` on web uses the browser file picker,
  while on iOS/Android it uses the native camera. Both work without code changes.
- **Firestore indexes** for compound queries — none needed because we filter on
  exactly one field per query and sort client-side.
